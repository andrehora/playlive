# AGENTS.md

For AI coding agents working on **Playlive**: a browser-based end-to-end test runner. You write tests in a small YAML format, pick an example site, press **Run**, and watch the steps happen in an iframe. Tests export to Playwright and Cypress.

Everything is client-side and buildless: the files are served exactly as they are. There is no bundler and no install step, but the app must be **served over http** rather than opened from disk, because it uses ES modules.

## Layout

```
index.html                The page: markup only, plus <script type="module" src="src/main.js">
src/app.css               All of the app's styles
src/*.js                  The app, as ES modules (see below)
examples/<id>/index.html  One example site per folder, a real page the iframe loads
examples/<id>/tests.yaml  That site's example tests
examples/<id>/bugs.js     Optional: ways that page can be broken, for a bug hunt
examples/examples.js      The manifest: name, category, host, accent, storage keys
examples/site.css         The stylesheet every example page shares
examples/hooks.js         Loaded first by every example page: $(id), error and storage hooks
tests/unit/               Playlive's unit tests: node --test, jsdom (dev only)
tests/e2e/                Playlive's Playwright suite, driving the real app (dev only)
tests/server.mjs          The static file server both suites are served from
```

The modules, roughly in dependency order: `dom` (elements) · `state` · `util` · `icons` (one SVG per category) · `sites` (loading a site, saved tests) · `find` (locating elements, "did you mean…?") · `actions` (what a step does) · `parse` · `history` · `snapshots` · `htmlview` · `results` · `run` · `recorder` · `catalog` · `coverage` · `bugs` · `complete` · `exports` · `dialog` · `picker` · `share` · `editor` · `ui` · `layout` · `modes` · `main` (wiring and boot).

Three rules keep the modules working without a bundler:

- **Only `main.js` boots anything.** Other modules may register their own listeners, but nothing calls across modules at load time. Import cycles are fine as long as that holds.
- **Shared mutable state lives in `state.js`** (`running`, `stopRequested`, `currentSite`, `editorSite`, …). Reading an imported binding gives the current value, but only the declaring module can assign, so each one has a setter: `setRunning(true)`, not `running = true`.
- **A module nothing imports from never runs.** `main.js` carries `import './dialog.js';` for exactly that reason.

Runtime dependencies are **js-yaml 4.1.0** from cdnjs (global `jsyaml`) and IBM Plex from Google Fonts. Do not add CDNs, frameworks or a build step without being asked. The dev dependencies include **js-yaml pinned to that same 4.1.0** and **jsdom**, both for the unit tests only; the js-yaml pin has to follow the CDN version, or the tests would parse differently from the app. Keep every path relative, so the app works from a subfolder on GitHub Pages, and keep images inline: the published page runs under a CSP that allows **no remote images**, which is why the framework logos are inlined SVG.

## Checking your work

```sh
npm install && npx playwright install chromium   # once
npm run test:unit                                # ~2 seconds, no browser, no network
npm run test:e2e                                 # ~1.5 minutes, must be green
npm test                                         # both, unit first
npm run lint && npm run lint:css                 # eslint and stylelint, both must be clean
npm run serve                                    # http://localhost:4173
```

**Two suites, and which one a check belongs in.** A question that is a function
of a string or a page — does this file parse, what does this export say, what
does this smell of, what would autocomplete offer here — belongs in
`tests/unit/`, where it runs in a couple of seconds and names the module it is
about. A question that needs a browser to answer honestly — is this element
visible, did this run go green, does this panel fold without the page
scrolling, do these keys reach the right control — belongs in `tests/e2e/`.
Nothing is asked twice: when a rule moves to a unit test, the Playwright test
that drove it through the editor goes, and the spec's header says where it
went. `npm run test:unit:watch` reruns the affected file on save.

Linting is dev-only, like the test suites: nothing is compiled and the files are still served exactly as they are. `eslint.config.js` lints `src/`, `examples/` and `tests/`; `.stylelintrc.json` lints the two stylesheets, with the stylistic rules that argue with this sheet's style turned off (one rule per line, `rgba()`, `(min-width:901px)`, ids named after their elements) and the ones that catch mistakes left on. Inline `<style>` and `<script>` in the HTML are not linted. Both have a `--fix` twin: `npm run lint:fix`, `npm run lint:css:fix`.

**The unit tests** run on `node --test` with no browser. Every module imports `dom.js`, which reads the page's elements at load time, so `tests/unit/env.mjs` builds a document from the real `index.html` with jsdom, loads js-yaml under the global name the CDN script gives it, and hands back `load()` for a module, `site()` for markup in the app's own iframe, `spec()` for the editor's file and `corpus()` for all hundred examples' tests read off disk. Three things to know about that environment: a module has to be imported *after* the document exists, so the tests use `await load(...)` rather than a static `import`; jsdom has no layout, so `getClientRects` is empty and `visible()` is false for everything — nothing in `tests/unit/` may ask whether an element is visible; and frames are queued rather than run, because `editor.js` keeps a standing `requestAnimationFrame` loop that is right in a browser and endless in Node (`flushFrames()` runs the ones that piled up).

**The Playwright suite** starts its own server and needs network access for js-yaml. It runs one worker per core rather than Playwright's default of half, because a run is mostly the browser waiting on the app it is driving; CI gets two, since oversubscribing a hosted runner only makes a run flaky. It derives the site list from `examples/examples.js`, so a new example site gets a test automatically. The **Flaky** category is excluded from the run tests, because those examples fail on purpose; the category itself is what says so (`SKIP` in `examples.spec.js` reads the manifest), rather than a list of ids kept by hand. They are still covered by the export tests and by the smells corpus — both of which are unit tests now, and read the files rather than the app.

Between them they already cover: the YAML format and every error it gives, both exporters over all hundred examples, every smell rule and what the rules make of the corpus, what marks a Create brief done and that every example's own file answers its own briefs, what a step credits in coverage, how the catalog lists and keys an element, what autocomplete offers for a given caret, the editor's line maths, the shape of a shareable link and the manifest's own rules — all of that in `tests/unit/`; and in `tests/e2e/`, every example site's tests passing with no page errors, light/dark/390px, the hundred real pages offering only targets that resolve, the panels and their folds, and the keys the suggestion list owns. If you touched layout, also screenshot and look — the desktop page must never scroll, panels scroll inside themselves. Add a test alongside any new action, exporter rule or site, in whichever of the two suites can answer it without a browser.

## The YAML format

```yaml
vars:                       # used as ${name}; ${unique} is new on every run
  email: ana@example.test
beforeEach:                 # runs at the start of every test
  - fill: { label: Email, value: "${email}" }

test: Shows the dashboard   # every test starts with "test:" at column 0
steps:
  - fill: { label: Password, value: hunter2 }
  - click: { role: button, name: Log in }
  - expectText: Welcome back
    timeout: 8000           # optional per-step wait, in ms
```

- Tests are top-level `test:` blocks, titled with `test:`. There is one way to write a file: shapes the format used to have — a `tests:` list around every test, a `site:` line naming the example, a `flows:` block pulled in with `- use:` — are gone from the parser rather than kept working, and a file using one gets the ordinary "Unknown setting" or "unknown action" error.
- Each test starts from a fresh page at `/` and must not depend on other tests.
- Only `vars`, `beforeEach` and `failOnPageErrors` may appear before the first test, and anything else there is named as an unknown setting. A file belongs to whichever site is selected, so it never names one. A step is written where it runs, and shared openings go in `beforeEach:`.
- Targets describe what a user sees: `{ role, name }`, `{ label }`, `{ placeholder }`, `{ text }`, or a bare string meaning `{ text }`.
- **The value goes inside the target**, so a step is one line: `- select: { label: Country, value: United Kingdom }`. A `value:` on its own line is an error that says so. Inside the braces, quote any value holding `,` `:` `{` `}` or a `${var}`: `value: "${email}"`.
- `timeout:` goes inside the target too, or on its own line for the steps that have no target (`expectText`, `expectNoText`, `wait`). `expectTextInRange` has braces without a target, and takes its `timeout:` in them or on its own line.

Actions: `click`, `fill`, `select`, `check`, `uncheck`, `wait`, `expectText`, `expectNoText`, `expectTextInRange` and `expectVisible`. There is no navigation step: a test starts on the site's page and stays there, and the exports open `/` for every test. Steps wait up to 4s (`TIMEOUT`) unless they set `timeout:`.

**`expectTextInRange` checks a number that moves.** `- expectTextInRange: { text: Ends in, min: 1, max: 24 }` reads the **first number on the page's first visible line holding that text** — commas taken out, so `12,400` is 12400 — and passes while it is between the two ends, inclusive. It is the fix for a check that is true only on the day it was written: a countdown, a count that grows, a draw of one to six, a computed value with a healthy band (`bmi-calculator` says exactly that). It is an assertion like the others, so it answers an Unknown Test, and it is the one check with no target, which is why both exporters read the page's text rather than a locator — keep the three readings the same if the rule ever changes. A missing text, a missing or back-to-front range, or a key that is not `text`, `min`, `max` or `timeout` is an error that says what to write instead.

Adding an action means updating **all** of: `ACTIONS`, `normalizeStep`, `describeStepBase`, `toPlaywright`, `toCypress`, `ASSERTIONS` in `parse.js` if it is a check, `KINDS` in `complete.js` if it takes a target, and one example site that uses it — one the run tests actually run, which the **Flaky** examples are not.

## Adding an example site

Three things: a folder with a page and its tests, and a line in the manifest.

```html
<!-- examples/coupon-code/index.html -->
<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<title>Coupon code</title>
<script src="../hooks.js"></script>
<link rel="stylesheet" href="../site.css">
<style>:root{--accent:#b45309}</style>
</head>
<body>
  …
  <script>…</script>
</body>
</html>
```

```js
// examples/examples.js
"coupon-code": { name: "Coupon code", category: "Shopping", host: "localhost:3022", accent: "#b45309" },
```

- **Order matters.** Categories run in manifest order and ports run 3001–3100 down that list, but **within a category the sites are sorted by name**, so adding one inserts it alphabetically rather than at the end. **Shopping** leads, and the first site of the first category is home, so `/` and `#address-form` are the same page.
- **One theme per category, one word.** A category names a kind of app someone would recognise, never a mechanism, and a name that wants two words keeps the first. The sixteen, in manifest order: Shopping, Support, Accounts, Admin, Travel, Banking, Search, Social, Inbox, Productivity, Media, Health, Dashboards, Learning, Games, Flaky. There is no **Forms** category: a form is a widget, not a kind of app, and every theme has forms in it. There is no **Misc** either, and that is the point: a catch-all is where a site goes when nobody has decided what it is, so a new example either fits a theme or is worth a theme of its own. The three that used to sit there found one — an order history that fails first time is **Shopping**, an offline banner is **Support**, a counter is **Productivity**. **Flaky** is the one category named after a mechanism, because the mechanism is the lesson: one small app, **Weather app**, whose readings are not the same every time — the station usually repeats itself and about one call in four sends something else, so the temperature moves over 0 to 30 and the wind over 5 to 100. The file says those two ranges in a comment at the top and nothing else, because what the page can send is the one thing the tests cannot tell you. Its page looks like any other example and so do its three tests: two are an `expectText` on the number the station usually sends, so each passes about three times in four, which is the whole point — a test that always fails is a broken test, and only one that mostly passes teaches what a flaky suite costs you. The two draws are independent, so a different one goes red each time rather than both together, and the repetitions control is how you watch that happen. Their fix is `expectTextInRange`, the one check in the format for a number that moves, and it is not in the file: this is the example you meet that action's problem in and `bmi-calculator` is the one you meet its answer in. The third test reads today's date, and no range saves that one: it was true the day somebody wrote it, and its fix is to check the label the page always carries rather than the day it happens to show. All of which is why it is the one category the run tests skip. It stays last. A new site goes here only if being unreliable is the whole point of it.
- **An icon per category,** living in `icons.js` as inline SVG (24x24, stroke-only, so `svg.i` sizes it and `currentColor` tints it). It is drawn in three places, each tinted with the category's accent: the picker's category heads, which sit on a band of that accent so a scroll through a hundred examples reads as sixteen groups, the example button in the app bar, and the Site panel's badge — so the colour groups and the icon names. The band and the badge share one mix, the accent at 16% behind text of the accent at 62% towards the ink, which is what keeps every one of the sixteen legible in both themes. A category with no icon of its own falls back to the neutral `fallback` one, which means a theme added to the manifest alone still looks finished; give it its own icon in the same change.
- **Accent per category,** in both the manifest and the page's `--accent`: Support `#0f766e`, Accounts `#1d4ed8`, Admin `#475569`, Shopping `#b45309`, Travel `#0e7490`, Banking `#a16207`, Search `#0369a1`, Social `#be185d`, Inbox `#4338ca`, Productivity `#7c3aed`, Media `#a21caf`, Health `#4d7c0f`, Dashboards `#5b21b6`, Learning `#78350f`, Games `#9f1239`, Flaky `#b91c1c`. **Flaky** is red because its pages are the ones that break; it is the only accent close to another — Games' crimson — and a page's own `--accent` is a separate palette from the `--pass`/`--fail`/`--running` tokens, which keep their meanings in the app's chrome. Sixteen is about as many hues as this scheme carries, so the order keeps lookalike pairs apart, and a seventeenth theme needs the picker to group themes under coloured sections instead. The picker reads a category's dot from its *first* site's accent, so a page that disagrees with the manifest makes the dot lie rather than failing.
- **Write ordinary HTML and JavaScript.** `hooks.js` gives every page `$(id)` for `document.getElementById`. The page is a real file, so there is nothing to escape.
- A site that writes storage keys before Playlive can see them lists them as `storageKeys` in the manifest, so **Reset** still clears them.
- **Make it testable the way a person would describe it:** real `<label for>`, real buttons, and an `aria-label` when buttons share text ("Add Coffee beans to cart").
- **Keep it deterministic.** Only the **Flaky** category may be random, slow or clock-dependent. A game picks a fixed card or move order rather than shuffling.
- Give it a kebab-case id, used as its folder name, name it after what it demonstrates, and write 2–5 tests covering the main path and its errors.
- **`expectNoText` sees every bit of visible text, `<option>` labels included,** so asserting that a row is gone needs a string the row's `<select>` cannot also hold: `"Invoice #4821 · no label"`, not `"Invoice #4821"`. A `#` in a target must be quoted too, or YAML reads it as a comment.

## Conventions

- **Colors mean things.** Grey `--active` is running, green `--pass`, red `--fail`. Yellow `--running` is the line a run is on in the editor and the HTML view, and the coverage score's middle band. Blue `--run` is for interactive controls only — never show progress in blue. The coverage score uses those three as bands: green at 100%, `--running` from 60% (its readable `--running-ink` where the colour is text), red below it, and its groups are green used, `--warn` checked only, red untested — with the dots differing in shape as well, solid, ringed and hollow, so the list never leans on colour alone.
- **Theming.** Define every color three times: light, `prefers-color-scheme: dark`, and `[data-theme="dark"]`.
- **Sizing is mobile first.** `:root` holds the touch-sized control tokens (`--tap`, `--btn-font`, `--btn-pad`, `--ctl-font`, `--icon-tap`, `--chev`, `--code-font`, `--code-line`, …) and `@media (min-width:901px)` redefines them smaller for a mouse. Size controls with the tokens rather than with literals, so both ends follow; `--ctl-font` stays at 16px on phones because anything smaller makes iOS zoom on focus. A test measures every visible control at 360, 390 and 768px.
- **Scrolling.** Never call `scrollIntoView` inside the iframe; it scrolls the outer page. Use `scrollWithinFrame` and `followInResults`.
- **Following is not optional.** The editor marks the line of the running step, Results keeps that step in view, and the HTML view keeps its line in view. There are no toggles for it: a run is meant to be watched. The Results head counts the run in circles under **Steps:**, one per step and cumulative over the whole run rather than the test running now. They are all drawn before the run starts, hollow, and fill in as it reaches them, so the row says how long the run is as well as how far it has got; a test that fails part way leaves the steps it never reached hollow. Beside them a summary says how far it has got and names no test: the circles are the detail, and a run of repetitions ends the same way, on its count of runs and nothing after it, because which test went both ways is what the row's **flaky** badge is there to say. They describe that run, so an edit clears them with the summary.
- **Results** are folded by default, and folds the user opens stay open across runs (`expandedTests`). The **flaky** badge is for a test that passes and fails without being changed, so a test that is failing now never carries it: it is failing, and that is what the row says.
- **Modes say what the app is for right now** (`modes.js`), and the choice sits in the app bar left of the example, because it decides which panels exist rather than what one of them shows. They run in the order you would meet them: **Explore** is the examples and their tests, **Create** takes the file away and asks you to write it back from the titles alone, then the three that judge what you ended up with — **Coverage**, **Mutation** and **Smells**, each with one panel of its own. A mode is one question and the panel that answers it: Mutation showed Coverage above its own panel once, and two scores in one column only asked the reader to work out which one they were looking at. The selected button is filled, ink on panel, rather than merely lifted like the other segmented controls: the mode governs the whole column, so the bar says which app this is from across the room. The mode is on `<html>` as `data-mode`, which is how the stylesheet both hides the panels a mode has no use for and starts the column at heights the ones it has will fit in; `index.html` ships the attribute set to Explore so nothing flashes before the module runs. The value lives in `state.js` beside the other shared state, because the picker, the sites and the editor all read it and none of them should have to import a panel to; `modes.js` owns what changing it *does*. Boot passes `{ initial: true }` so the handovers below do not run against an empty editor. It is kept in `:layout`, like the column widths — it is about this browser rather than the examples, so **Reset** leaves it alone — and a change re-clamps the stored heights (`reclamp` in `layout.js`), because a column dragged tall in one mode need not fit in the next. Leaving Mutation repairs an injected page: nothing should outlive the panel that explains it. It is **half the share link**: `#create#coupon-code` is that example in that mode, so a link points at what you were doing as well as what you were looking at, which is what makes an exercise something you can hand to somebody. Each half is left out when it is the default — home is the first example and the first mode is Explore — so `#coupon-code` still means exactly what it always did and every link written before modes existed still opens. A link's mode wins over the one the browser remembers. `hashchange` reads both halves before applying either, because changing the mode writes the address and would take the example out of the hash before it was read. More modes are expected, so adding one means a `MODES` entry, a button in the seg, and the CSS that says which panels it has.
- **The feature is called Mutation on screen and `bugs` in the code.** The mode, the panel, its score and its button say mutation, because that is what injecting one change at a time and asking whether the tests notice is called. `bugs.js`, `#bugs`, `data-mode="mutation"`, `examples/<id>/bugs.js` and the manifest's `bugs: true` keep the older name; renaming them is a mechanical change across a hundred examples and has not been made. Copy says mutation, code says bug.
- **The left column holds as many panels as the mode has:** Tests and Results in Explore, and the mode's own panel third in each of the other four, with a handle between them. Results folds in three stops from one button, which always says what the next press does: the steps of every test shown, then hidden, then the panel itself down to its one row. Collapsed, `#results` goes, Coverage takes the space it gave up, and the editor may grow into it. Coverage folds the same way: folded it is its one row, Results takes the room back, and its own handle, having no height left to set, keeps its place but stops taking the pointer. With both lists down to a row the editor takes what is left, so the column is never half empty — which is why `clampEditor` measures the Results floor rather than assuming it. Its own handle has nothing below Results left to split, so it moves the one boundary above it that can still give — the editor's — and goes on meaning what it always meant: drag Coverage's top edge. The head still carries the summary and the run's circles, so a run stays readable from that one line. Coverage's height is `--cov-h` in the layout, Mutation's is `--bug-h`, Test smells' is `--smell-h`, Create's is `--create-h`, the editor's is `--editor-h`, and the clamps in `layout.js` are what keep the desktop page from ever scrolling: no handle may squeeze the panel below it past its floor, and in Mutation the Tests panel gives way too rather than being the one thing that cannot shrink on a short screen. The clamps measure what is on screen rather than asking which mode is on — a panel the mode does not have measures zero and asks for nothing. **Folding the code is a fold like the others**, `data-spec` on `#left` beside `data-results`, `data-cov` and `data-smells`: the room it gives up goes to the list with the most to show — the mode's own panel, in every mode that has one — rather than stretching Results past its own rows, and in Explore, where Results is the only list there is, it still takes it all. Two rules hold across every combination of folds, and a test sweeps all of them in all four modes: **a folded panel is never the one that grows**, so a fold can never leave a panel stretched over the body it has stopped drawing, and the room always goes to something that has content — falling back to Results, then to the editor. Fold everything and the column simply ends: a gap is honester there than a blank panel. A fold that leaves nothing above a handle hides that handle, and a handle whose panel can no longer give moves the one boundary above it that can — the editor's (`editorForHandleTop`, which Coverage's handle and Test smells' both use). On a narrow screen the panels stack in order, the site between the first two.
- **On a narrow screen the test code starts folded.** The panels stack there, so a screenful of YAML would push the site and its results off the bottom; `main.js` folds the editor at boot under 901px and the Tests panel's own button brings it back. The file is untouched either way, so running, recording and exporting do not care.
- **Choosing the mode and the example lives in the app bar**: the mode first (`modes.js`), then the example (`picker.js`) — its name with its category icon and pass/fail dot, its list, the stepper that walks the 100 examples — and **Reset**, so the two things every panel below depends on read first. There is no separate reload: Reset is the one way back to the start, and it is global rather than per site: it reloads the page showing and clears everything the app kept for *every* example — saved tests, the sites' own stored data, run history, statuses, catalogs, edited markup and the last result — leaving none of our keys in storage (layout and theme, which are about this browser rather than the examples, stay). `resetAll` in `main.js` owns it. The site panel's own head keeps what is about the page on screen — Site/HTML and screen size. On a phone the bar is exactly three rows, each using the whole width: the mark and name with **Reset**, **Share** and the repository spread across the rest of the first — they keep their names and tighten to fit, which is what the rows below are for — then the mode taking the second whole, two names at half the width each, then the example's list and its stepper sharing the third 60/40, so a name as long as “Address form” still reads while “1 of 100” keeps its arrows. The site panel's head fills its two rows the same way, the page with its category and the reload across the first, then Site/HTML across the whole second.
- **The site panel has two views,** Site and HTML, remembered in the layout. The HTML view (`htmlview.js`) reads the markup back out of the live page after every load and every step, so typed values and revealed screens are really there, and marks the line of the element the step acted on green or red, following it the way Results follows a step. The action's own name goes in the gutter, in place of that line's number: the gutter is already a lane down the left, so the name reads where the eye starts and the markup beside it never shifts to make room for it, which is why that lane is a fixed width. The page stays laid out underneath, covered rather than hidden: a step can only find an element the browser is still giving a size to.
- **The markup is editable.** The HTML view is a textarea over a highlighted copy of itself, the same shape as the test editor, coloured line by line by `hlMarkupLine` whether the line came from the page or from what is being typed. Edits do nothing until **Save**, which writes the markup back as `srcdoc` (plus the runner's own `<base>`, which the view skips) so the page is parsed again and its scripts run: the buttons still work, and what the page held in variables starts over. Saved markup then **is** that site's page, kept per site in `editedHtml` in `state.js` and served by `loadApp`, so a run starts every test from it; **Reset** clears it and brings the file back. It is never stored, like the catalog. Saving harvests the catalog again, so new elements are offered by autocomplete — but harvests only add, so names an edit removed linger until **Reset**. While there are unsaved edits the view stops reading the page, and **Revert** or any page load drops them.
- **The test editor does not copy or paste.** Copy, cut, paste and a dropped selection are all refused on `#spec` (`REFUSED` in `editor.js`), each with a line saying why rather than a control that quietly does nothing: writing the step is the exercise, and a file that can be shuffled from one example into another — or pasted in from outside — turns Create into a copying exercise with the answer one mode away. **Export** is the deliberate way out, a button that says what it is handing you. The runner, the recorder and Playlive's own tests write the file through its value rather than the clipboard, so none of this is in their way.
- **Toolbar order** is Run, Stop, Record; in Step by step mode Run becomes Next step, with no separate button. The per-test button in Results is also called Run, labelled “Run only <title>” for screen readers.
- **Shareable links.** The mode and the example showing are the URL's hash (`.../#create#coupon-code`, each half left out when it is the default), so a link opens what you were doing, and **Share** in the app bar copies that link. `share.js` owns it: boot reads the hash, and with no hash (or an unknown id) opens the first example in the manifest, in the first mode, rather than the one visited last, `selectSite` replaces the hash rather than pushing it (walking 100 examples must not fill the back button), and `hashchange` follows a link pasted into the bar. The hash is used rather than a query so the link works from a subfolder on GitHub Pages with no server rule behind it. The name and icon in the app bar are a link to `./` — home, which is the first example, so `/` and `#address-form` show the same thing; the link is relative so it stays inside a subfolder. `index.html` is dropped from the link and from the address bar, so what Share copies and what the bar shows is `.../#newsletter-signup`, never `.../index.html#newsletter-signup`.
- **Copy** is sentence case, with error messages that say how to fix the problem.
- **Accessibility.** Visible focus rings, real labelled buttons, `aria-pressed`/`aria-expanded`, keyboard support in the picker and dialog, `prefers-reduced-motion`.
- **Storage.** Nothing about bugs is stored, like the catalog and the coverage score. Keys carry no version suffix: `live-test-runner` (tests per site), `:create` (what you have written in Create mode, per site), `:history`, `:status`, `:site-keys`, `:layout` (the two column widths, the editor and coverage heights, the site view and the screen size). Wrap every access in `try/catch`, and read defensively so a stored shape you no longer write cannot break a load — every read already falls back to its default on anything unexpected.
- **The site catalog.** `catalog.js` reads the live iframe into a per-site list of what a step could target: clickables, fields, selects and their options, toggles, and the page's text. It reads the page exactly as the recorder does, through `targetParts`, so anything it offers is something `find.js` can locate. Hidden elements are kept (an error message already in the DOM is a fair `expectText` target) and harvests only ever add, so a screen a run passed through stays known. It is harvested on every frame load and after every step, cleared for every site by **Reset**, and never stored.
- **UI coverage.** `coverage.js` is the catalog joined to the run: of the controls a site offers — the catalog's clickables, fields, selects and toggles, never its headings or text — how many did the tests actually use? What counts is measured as the run happens and never by reading the file: a step that passed credits the element it landed on, under the very key `catalog.js` lists that element under (`keyFor`), so `- click: Apply` credits the entry written `{ role: button, name: Apply }` and there is no second matching rule to keep in step with `find.js`. What `beforeEach` does and `${unique}` come free, because a step is credited after it ran. Each control ends up **used** (a `click`, `fill`, `select`, `check` or `uncheck` landed on it), **checked only** (an `expectVisible` or `expectText` did, which is not the same thing and reads as its own group) or **untested**; hidden ones stay in the denominator, because a control behind a screen no test opens is exactly what should count against you. A full run clears the score first, so it describes that run; running one test adds to it. Like the catalog it is never stored, and **Reset** clears it. A select counts as one control and says how many of its options a test has picked. Every untested row carries **Add test**, which writes a whole `test:` block for that control at the end of the file through the recorder's `addTest` — a control nothing reaches needs a test of its own, not a step bolted onto whatever test happens to be last — so the panel is a to-do list rather than a report. The title says what the test does (“Clicks Apply”, “Fills Coupon code”), numbered if the file already holds that title, and an empty file is fair game: what the button will not write into is a file that does not parse. The button goes once it has written its test and the row reads “test added” instead: the file is the record, and a second click would only repeat it. A full run or **Reset** settles that mark, the way it settles the score.
- **Bugs.** Coverage says which controls a test touched; it cannot say whether the test would notice the page going wrong, and a green 100% that catches nothing teaches the wrong lesson. So a site may ship `bugs.js` beside its tests — a list of `{ id, title, find, replace }`, each one a patch on the page's own source — and say `bugs: true` in the manifest, which is what stops the app fetching a file that is not there. **Run mutations**, in the panel's head in Mutation mode, runs them: it runs the suite once against the page as it ships, refuses to go on unless that is green (a red suite would call every bug caught), then injects each bug in turn and runs the suite against the broken page. A bug the tests fail on is **caught**; one they all pass is **escaped**, and the escaped group leads the list because it is the work left to do: each row names a test nobody has written. A `find` that no longer matches is reported as **no longer applies** rather than scoring for free, so editing a page cannot inflate the number. The bug is served the way edited markup is, as `srcdoc` from `bugHtml` in `state.js`, so every test in a run meets the broken version and the HTML view reads it back as code; **Inject** leaves one on the page to look at or run by hand, and something always says so: a red bar over the site, or, when the markup is showing, the same message in the row that already holds Revert and Save, since that view has a row of its own and a second one would only cost space. The HTML view marks the line the bug changed, named `bug` in the gutter, and scrolls to it — a line counts only if it holds the new text and is not a line the page always had, so a snippet that appears elsewhere is not marked. `bugs.js` pushes that mark into `htmlview.js` rather than being read from it, so the view never calls across at load time. A hunt breaks the page on purpose, so `hunting` keeps its failures out of run history, out of the site's pass/fail dot and off the coverage score. Like the catalog it is never stored, and **Reset** clears it. Adding a bug means a plausible mistake and a `find` that appears **exactly once**; adding a site's first bugs means the file, the manifest key, and a test.
- **Create.** `create.js` takes the file away. The editor starts as nothing but the titles of the tests the example ships, written as comments, and the panel says how many are still yours to write. The titles are the whole brief, deliberately: “Shows an error for a missing ZIP” says what the test must prove without saying which control to click, which is the part worth working out. The example's real tests are still there — every other mode is reading them — so the answer is one mode away rather than hidden. **It is the one mode that changes what the editor holds**, so it keeps a file per site of its own: `createTests` beside `savedTests` in `sites.js`, chosen by `bufferFor(mode)`, stored under `:create`, and cleared by **Reset** like the rest. Every read and write of the editor goes through `testsFor`/`stashEditor`, so neither file can overwrite the other — a change of mode, of example or a reload hands each side back exactly what it had, and a test asserts all three. A title is **done** when the file holds a `test:` with that title **exactly** and that test makes every check the example's own test makes — each `expectText`, `expectNoText` and `expectVisible` among its own steps, never one inherited from `beforeEach` (on either side). The title says which brief you answered and the checks say you answered it; the steps that get there are yours, and there is usually more than one way, which is the point. `ASSERTIONS` in `parse.js` is the one list this and the Unknown Test smell both read. A test that checks nothing is not offered as a brief at all (`titlesOf` skips it): a brief is “prove this”, and there is nothing there to prove or to mark done — which is also what lets an example ship an Unknown Test for Smells mode to point at without failing its own briefs. The panel reads as a board — **TODO**, **DOING**, **DONE** — which is the one place the app shouts, because they are column names rather than sentences. The score is the done count out of the titles, banded like the others; it does not ask the run, so the panel follows the file as it is typed. A test asserts that **every example's own file scores full marks against its own briefs** — the answer key has to be a valid answer, in all hundred of them, or the rule is asking for something unreachable. Rows go to their line: the test if it is written, its comment if not.
- **Test smells.** `smells.js` is the third score and the only one that reads the *file* rather than a run: some of what makes a suite hard to trust is visible before anything runs. It redraws from `preview()`, so it follows the editor as it is typed. Each smell is a heuristic **with a name**, and the name is the point — a student who can say “that is Duplication of Setup” has something to look up — so the panel prints the sentence that explains it under the name rather than hiding it in a tooltip. One sentence: what is wrong and what to do. Every row goes to the line it is about (`jumpToLine` in `editor.js`, which the error box uses too). A smell with no line to show is not offered. **Unknown Test** is a test with no check of its own — `ASSERTIONS` in `parse.js` is the list, and `expectTextInRange` counts like the rest; `beforeEach` assertions do not, because they are not what *this* test claims. **Eager Test** counts a test's **assertion phases** — runs of checks, separated by the steps in between — and names one at four or more: a test that acts, checks, acts, checks, acts, checks, acts, checks is four tests wearing one title, and the Results row can only name the first of them that broke. A phase is one run however many checks are in it, because proving one thing can take several. The threshold is `EAGER` in `smells.js`, and four is where the corpus put it: of the 340 shipped tests, 302 stop to check once, 31 twice, two three times, and the only three that stop four times are the three written to be found. It pairs with **Duplication of Setup** — splitting an Eager Test leaves the same opening in each half, which is exactly what that one then tells you to move into `beforeEach`. **Assertion Roulette** counts the checks where Eager Test counts the phases, and names a test at more than five: a step here carries no message of its own, so when one of a long row of checks goes red, the row is all there is to read. The threshold is `ROULETTE` in `smells.js`, and five is where the corpus put it — of the 340 shipped tests, six make four checks and only the two written to be found make six. A test can be both, because they are different diagnoses: one says it proves several things, the other that nothing says which of its claims was the point. **Magic Value** is a value — what a `fill` or `select` types — written out on more than one line: once is a value, twice is a value with no name, and `vars:` is where a name goes. It reads the *value*, not numbers inside a check's text, because “Count: 3” is the words of a message rather than a constant somebody supplied; counting those flagged 93 of the hundred examples, counting values flags ten, and each of the ten is a real duplicate. A value that came from a `vars:` entry is not written on its own step's line — that line says `${name}` — so a file that has already named one has nothing to answer for, which is also how the rule says what the fix looks like. **Duplication of Setup** is every test opening with the same steps: that is the suite's setup written out once per test, and `beforeEach` is where setup goes. It takes at least two tests, it compares a test's *own* steps (what `beforeEach` already provides is not repetition), and it reports the shared opening step by step, each row going to the line that would move. A smell that cries wolf teaches people to ignore the panel, so each one is written to stay silent when it is unsure, and a file that does not parse is left to the error box. **The panel has two tabs, because it answers two questions.** **This file** is what the tests on screen smell of. **All smells** is the catalogue: every smell the app looks for, named with its sentence whether or not anything has it, and under each the examples that do — read from every example's file the same way the panel reads the one on screen (`scanSites`, once per entry to the mode, never stored, `found` in `smells.js` keeping each example's findings beside the `smelly` set). A student who has never met Assertion Roulette should be able to find out that it exists without first writing one, so a row there opens that example, in the file tab, at the line it is about — the catalogue is a way into the hundred examples rather than a glossary. It follows the editor as it is typed, like the other tab: write a smell into the file on screen and your example appears in it. The tab is never stored, like the catalog. The mode does **not** narrow the example list: it did once, and hiding the clean examples hid the ones worth comparing the smelly ones with, as well as making the list change length under you. The panel is where "which examples have one" is answered. The panel starts at a height of its own (`--smell-h` in Smells mode) rather than at the height of whichever list is showing, so switching tabs moves nothing: both lists scroll inside it. The panel bands in two, not three: `--warn` when it found something, green when it did not. It folds the way Coverage does — folded it is its one row, the count stays, and Results takes the room back. Almost every example ships clean: the corpus test pins what the rules make of all 100 of them, so a new example with an accidental smell in it fails the suite. Seven tests are deliberately smelly — two Unknown Tests, three Eager Tests and two Assertion Roulettes, each with a comment above it saying so — because a panel that names five smells and can only show you two of them teaches half of what it knows. They are spread over seven examples rather than hidden in one. An Unknown Test is the one deliberate smell that changes another mode: **Create** does not offer a brief for a test that checks nothing (`titlesOf` skips it), because a brief is "prove this" and there is nothing there to prove or to mark done. Adding a smell means an entry in `SMELLS` with its sentence, a rule in `report`, a test for both what it catches and what it must not, and — if nothing in the corpus has it — an example that does.
- **Coverage and Mutation are two panels in two modes, never both at once.** Each carries its own score, its own band and its own bar, in the same three colours: green at 100%, `--warn` from 60%, red below. The Mutation panel folds like the others — to its one row, score and **Run mutations** still on it, with Results taking the room back — and `data-bug` on `#left` is what says so, beside `data-results`, `data-cov`, `data-smells` and `data-spec`. **Run mutations** lives in its head, where the other panels keep their actions, and greys out with every other control while the runner is busy — `run.js` announces that as `playlive:busy` and `bugs.js` listens, the same way it listens for `playlive:site` when the example changes, rather than either module reaching into a panel it knows nothing about.
- **Autocomplete.** `complete.js` is two halves: `context()` reads the caret and says what may go there, `itemsFor()` fills that slot from the site catalog. An action only ever offers what it could act on, so `select:` lists that page's `<select>`s with their own options and `check:` only its boxes. It opens on the characters that start something new and on Ctrl+Space, closes when there is nothing left to choose, and owns Tab and Enter while it is open — which is what `completionOpen` in `state.js` tells the editor. The list is on `<body>` in viewport coordinates, because a panel clips what overflows it; on a phone it spans the editor instead of following the caret.
- **The test API.** `main.js` puts `window.playlive` on the page for Playlive's own tests. Add to it rather than reaching into modules from a test.
- **Exports** carry no comments and must keep the runner's meaning: fresh page per test, partial matching for `expectText`, visible text only for `expectNoText`, per-step timeouts, `${unique}`. Update both exporters when matching rules change.

## Known limits

- Same-origin pages only. Other local sites need a reverse proxy, or a script that talks to Playlive over `postMessage`.
- Clicks and typing are DOM events (`isTrusted` is false). Uploads, downloads, extra tabs and native dialogs are out of scope.
- Exports are syntax-checked, not executed; run each framework once for real before relying on it.
